- Repository: https://github.com/IT-Kamianets/3d-constructor-fixed-view
- Its current `AGENTS.md` is authoritative about the constructor, engine, package IDs, and Unity installation. Read it **before making changes**.
- The verified starter README says **Unity 6000.6** (Universal 3D/URP), `Assets/Scenes/Main.unity`, and that fixed-view camera/controls packages are not implemented yet. Do **not** assume either is available.

- Keep constructor project `AGENTS.md` intact and add a brief project-specific link to these guides, or merge guidance carefully. Do not silently erase shared rules.

Project settings: product `Temnorid: Escape`, suggested application identifier `com.itkamianets.temnoridescape` (confirm uniqueness within workspace), desktop Windows target, consistent version `0.1.0`.

## 2. Dependency and package policy

Use existing engine packages, in the order and versions prescribed by the live constructor guide:

- `3d-unity-core`: app initialization/services
- `3d-unity-scene`: shared scene representation when applicable
- `3d-unity-input`: **only permitted input entry point**
- `3d-unity-character`: reusable character controller
- `3d-unity-assets`: asset references/cache; **use only functionality actually present**
- `3d-unity-audio`: audio events

The constructor's `AGENTS.md` currently calls for building two reusable constructor packages: `3d-constructor-fixed-view-camera` and `3d-constructor-fixed-view-controls`. If absent, implement their minimal **game-neutral** versions as the constructor requires; keep them small and test them in two rooms. Do not create a new `escape-*` package or schema for this MVP. Game-specific systems, levels, prefabs and asmdefs stay under `Assets/TemnoridEscape/`. Only promote a generic implementation to an engine/constructor package when it is genuinely reusable and respects repository contribution rules. Avoid changing engine repos without need; if needed, make changes in an isolated branch/PR per the parent guide.

**Do not invent** `3d-*` package APIs, networking APIs, data schema fields, or prefab assets. Inspect source and README docs first, then write adapters against confirmed interfaces. No speculative dependencies; no Firebase; no paid assets; no Meshy/AI-model generation requirement; no bespoke backend.

## 4. Architectural boundaries

- `Boot/MainMenu` launches `Prison` and handles local save selection.
- `PrisonEpisodeState` owns the logical state; Unity scene objects render it, do not each own independent truth.
- `InteractionSystem` deals with proximity, line-of-sight and one active interaction target.
- `Inventory` supports **non-consumable clue items** and **explicit consumption** for used items, with unique item IDs.
- `PuzzleStateMachine` validates prerequisites and changes authored flags.
- `CameraZoneSystem` belongs to fixed-view constructor; *no game story or puzzle logic in it*.
- `GuardPatrol` performs lightweight, deterministic patrol and detection; it uses the active zone geometry but not the camera to detect players.
- `SaveService` persists serializable primitive IDs/flags; does not serialize scene objects or Unity references.
- `LordsContextAdapter` provides a **static/mock** capture context for this demo and emits a mock result. No outbound writes.

Avoid premature patterns (network service abstraction, plugin architecture, ECS, scriptable pipeline of arbitrary puzzle types). Keep content declarative where it reduces duplication; for exactly three hand-authored puzzles a simple state graph is sufficient.

## 6. Working style for autonomous execution

- Implement a **complete gameplay loop first**, not advanced artwork.
- Use Unity primitives for walls, doors, tables, locks, camera markers and the player if assets are unavailable. Avoid complex custom model pipelines.
- Favor a single level, few scripted interactions, deterministic puzzles and short playtime.
- Keep gameplay fully offline. A mocked Lords scenario is enough for demonstration.
- Never make unsourced assumptions about the current packages. If package names or current APIs differ, align with real code and record decisions.
- Do not silently discard failing tests or required features. Fix bugs, or document blocked items plainly.
- Provide a concise final summary: implemented scenes, controls, tests run (with actual results), build status, release link if real, outstanding work.
